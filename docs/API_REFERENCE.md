# A2Z MIS 360 — API Reference

This document is the entry point to the A2Z REST API. The detailed,
schema-accurate reference is auto-generated by FastAPI and served live by
the running API process. This file explains how to access it, what the
authentication model is, how the endpoint families are organised, and
how to consume the API safely.

## Live reference

When the API is running, two interactive specs are served:

- **Swagger UI:** `http://<host>:<port>/api/docs`
- **ReDoc:**     `http://<host>:<port>/api/redoc`
- **Raw OpenAPI JSON:** `http://<host>:<port>/openapi.json`

Default `<port>` is `8502` (override with the `A2Z_API_PORT` env var).

To produce a static copy of the OpenAPI document for offline distribution
or version control:

```bash
python scripts/export_openapi.py > docs/openapi.json
```

The generated `openapi.json` is the canonical machine-readable contract.
This document is the human-readable orientation.

## Authentication

Every endpoint except `/api/health` requires a Bearer JWT.

### Login flow

```http
POST /api/auth/login
Content-Type: application/json

{
  "username": "william001",
  "password": "ECOStaff001"
}
```

Response:
```json
{
  "access_token": "eyJhbGc...",
  "token_type":   "bearer",
  "expires_in":   28800
}
```

Use the token in subsequent requests:
```http
GET /api/dashboard/md
Authorization: Bearer eyJhbGc...
```

Tokens expire after 8 hours. There is no refresh endpoint — clients
re-authenticate when a 401 is returned.

### Threat model

The auth design closes vulnerabilities V-001 through V-004:
- **V-001** (no auth on API): every endpoint except `/api/health` declares
  `Depends(get_current_user)`. Audit gate G12 enforces.
- **V-002** (SQL injection): see Security Architecture document.
- **V-003** (XSS): tokens are signed; never reflected back as HTML.
- **V-004** (weak password storage): bcrypt via `_hash_password`. Audit
  gate G11 enforces.

## Endpoint families

The API is organised into two layers:

### Layer 1 — Curated read endpoints (`/api/*`)

Hand-written endpoints for the most common queries. These shape the
response to whatever the consuming page needs. Examples:

| Path | Purpose |
|---|---|
| `GET /api/dashboard/md` | MD-level rolled-up dashboard |
| `GET /api/bsc/summary` | Bank-wide BSC summary |
| `GET /api/bsc/staff/{username}` | Per-staff scorecard |
| `GET /api/pipeline/summary` | Pipeline aggregate (counts, value, by-stage) |
| `GET /api/pipeline/deals` | Pipeline deal list (legacy; prefer `/api/v1/pipeline_deals`) |
| `GET /api/credit/summary` | Credit portfolio aggregate |
| `GET /api/credit/watchlist` | Watchlist accounts |
| `GET /api/aml/summary` | AML alert aggregate |
| `GET /api/users/summary` | User count + role distribution |

### Layer 2 — Generic CRUD endpoints (`/api/v1/{module}/*`)

Generated by the `make_crud_router()` factory in `utils/api_crud.py`
(introduced in v5.31). For every PG-live module wired with the factory,
8 endpoints are exposed in a uniform shape:

```
GET    /api/v1/{module}              list (paginated)
GET    /api/v1/{module}/{id}         get one
POST   /api/v1/{module}              create
PUT    /api/v1/{module}/{id}         update
DELETE /api/v1/{module}/{id}         delete
POST   /api/v1/{module}/export       export (large page, no auth tier diff)
GET    /api/v1/{module}/search       search by configured columns
GET    /api/v1/{module}/dashboard    aggregate counts/sums for charts
```

Currently wired (`G16` tracks progress):
- `pipeline_deals` (v5.31 pilot)

Target: 17 modules × 8 endpoints = 136 endpoints (plus the 14 system endpoints
above = 150 total).

## Pagination

List + search + export accept:
- `limit` (int, default 100 for list, max 10000 for export)
- `offset` (int, default 0)
- `order_by` (string, allowed columns are configured per-module)

Response shape:
```json
{
  "rows":   [...],
  "total":  1234,
  "limit":  100,
  "offset": 0
}
```

## Error format

All errors return JSON of the form:

```json
{
  "detail": "human-readable message",
  "code":   "ERROR_CODE",
  "request_id": "uuid"
}
```

Status codes used:
- `200` — success
- `400` — bad input (missing field, malformed JSON)
- `401` — unauthenticated (no token / expired)
- `403` — authenticated but not authorized (RBAC denial)
- `404` — resource not found
- `409` — conflict (duplicate insert, optimistic-locking failure)
- `422` — validation failure (Pydantic schema mismatch)
- `500` — server error (always logged with the `request_id`)

## Caching

GET endpoints are cached in-memory with a default 60s TTL via the
`@cached` decorator in `utils/api.py`. Two cache-management endpoints:

- `POST /api/cache/clear` — flush all cached responses (admin only)
- `GET  /api/cache/stats` — hit/miss counts, current size

The cache is per-process. Multi-worker deployments accept that each
worker has its own cache.

## Rate limits

No rate limiting is enforced by the API today. Front the API with
nginx/Cloudflare for production rate limiting (Standard #5 load test
shows the API handles 1,000+ concurrent users without backpressure).

## Versioning

- Hand-written endpoints are stable as of v5.17 — breaking changes will
  be announced with at least one minor version's notice.
- `/api/v1/*` endpoints are versioned. `/api/v2/*` will exist when a
  breaking change is required; both will be served in parallel for one
  minor release before v1 is retired.

## Examples

### Full login + dashboard fetch (curl)

```bash
TOKEN=$(curl -s -X POST http://localhost:8502/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"william001","password":"ECOStaff001"}' \
  | jq -r '.access_token')

curl -s http://localhost:8502/api/dashboard/md \
  -H "Authorization: Bearer $TOKEN" \
  | jq .
```

### Create + list a pipeline deal (Python)

```python
import requests

base = "http://localhost:8502"
r = requests.post(f"{base}/api/auth/login",
                  json={"username":"william001","password":"ECOStaff001"})
token = r.json()["access_token"]
hdrs  = {"Authorization": f"Bearer {token}"}

# Create
new_deal = {
    "client_name":   "Acme Industries",
    "stage":         "Initial Contact",
    "deal_category": "Trade Finance",
    "unit":          "Corporate",
    "value":         500000,
    "currency":      "USD",
    "open_date":     "2026-04-29",
    "staff_code":    "300001",
}
r = requests.post(f"{base}/api/v1/pipeline_deals", json=new_deal, headers=hdrs)
deal_id = r.json()["id"]

# List
r = requests.get(f"{base}/api/v1/pipeline_deals?limit=10", headers=hdrs)
for deal in r.json()["rows"]:
    print(deal["client_name"], "—", deal["stage"])
```

## Audit hooks

Every state-changing endpoint writes an audit row via `utils/core_audit.audit_log`.
The trail is queryable from the admin UI (Admin → Audit) or directly via:

```sql
SELECT * FROM audit.audit_logs
 WHERE entity = 'pipeline_deals'
 ORDER BY created_at DESC
 LIMIT 100;
```

See the Security Architecture document for the audit contract.
