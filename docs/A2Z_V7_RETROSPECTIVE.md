# A2Z MIS 360 — v7.x Systems-Layer Campaign Retrospective

> **Status**: Canonical retrospective (v7.16, May 2026)
> **Scope**: 24 batches from v7.0 (foundation) to v7.15 (audit hardening)
> **Audience**: Future engineers who need to understand how the platform's systems layer was built
> **Supersedes**: per-batch CHANGELOG_v7.x.md narratives (those remain the source of truth for individual batches; this doc tells the arc)

---

## What v7.x was

A 24-batch campaign that took the A2Z MIS 360 platform from "engines + audit gates" to "engines + audit gates + a coherent systems layer that names every accumulator, every feedback loop, every regulated invariant, and every health composite — all wired, all visible to operators, all audit-hardened against regression."

The campaign's organising frame is **Donella Meadows' Systems Thinking** plus **Eric Evans' Domain-Driven Design** (see `docs/A2Z_SYSTEMS_CHARTER.md`):
- **Stocks** are the system's memory — the slow-changing accumulators (loan portfolio, deposit base, NPL inventory, capital base, customer base, dormant accounts).
- **Flows** are how stocks change — but more importantly, **feedback loops** are how the system *learns* from outcomes.
- **Hard invariants** are the threshold values that drive regulated decisions (CBK CAR ≥ 14.5%, LCR ≥ 100%, LDR ≤ 80%, etc).
- **Bounded contexts** are how the platform's domains stay decoupled (Charter §7 — Anti-Corruption Layer + Published Language patterns).

v7.x took the platform's existing 116 standards (engines built v5.53 → v5.70 + composites v6.0) and made them participants in a coherent system instead of a flat library.

## The 24-batch arc

### Foundation (v7.0 → v7.0.1) — 2 batches

The platform learned to talk about itself.

- **v7.0** Charter (288 lines, 14 sections) + 3 utility modules: `system_stocks.py` (6 stocks designed) + `system_flows.py` (15 loops designed) + `system_invariants.py` (8 invariants registered). 1 stock WIRED (capital_base via CapitalAdequacyEngine). 1 engine reading from registry (stress_testing). Page 91 systems-view created.
- **v7.0.1** 4 more engines migrated to invariants registry (capital_adequacy, liquidity_risk, regulatory_reporting, treasury_intelligence). Audit gate G104 added.

**Key insight from this phase:** Building the registry first, before any wiring, gave every subsequent batch a place to record decisions. The registry isn't optional documentation — it's the platform's ground truth.

### Functional landings (v7.1) — 1 batch

The platform connected the registry to a real domain page.

- **v7.1** Credit Risk depth on page 19 + 2 stocks WIRED (loan_portfolio + npl_inventory) + L01 wired (Collections → PD recalibration learning loop) + 6th engine (credit_risk_scoring) reading from registry + audit gate G105 (strict invariant migration enforcement).

This batch is the conceptual hinge of v7.x — the systems layer stopped being "infrastructure on the side" and became "the load-bearing structure of a domain page."

### Loops campaign (v7.2 → v7.6) — 5 batches

The platform learned to close feedback loops.

| Batch | Loops | Stocks | Highlight |
|---|---|---|---|
| v7.2 | 9/15 (60%) | 3/6 | L06 + L07 + L11 wired |
| v7.3 | 10/15 (67%) | 4/6 | deposit_base + L10 |
| v7.4 | 11/15 (73%) | **6/6 (100%)** | customer_base + dormant_accounts + L09 |

**Key insight:** Each loop closure was a specific producer engine + specific consumer engine + specific payload contract. The audit log entry for "L0X WIRED" became a meaningful event — outcomes from one bounded context now recalibrate behaviour in another.

### Functional depth (v7.7, v7.9) + UI surfacing (v7.8) — 3 batches

The platform exposed engine internals to operators.

- **v7.7** IFRS 9 Classification Engine depth on page 32 (6 method sections, interactive)
- **v7.8** **Biggest single-batch UI jump** — 4 composites surfaced on per-domain pages (workforce on page 2, RCSA on page 54, customer_value on page 34, AML on page 55 with LIVE customer_base read). Integration tally 55 → 59.
- **v7.9** IFRS 7 Disclosures Engine depth on page 88 (7 method sections; completes v7.1's planned triple-page Credit Risk depth campaign)

**Key insight:** The "uniform expander pattern" from v7.8 is now the canonical way to surface composites or engines on per-domain pages. v7.13 reused it for cards.

### ACL infrastructure (v7.10 → v7.11) — 2 batches

The platform built a permanent seam to FLEXCUBE.

- **v7.10** `utils/flexcube_aggregator.py` (new module) with mode-aware fallback (live → CBS synthetic → demo defaults). 3 stocks ACL-wired (loan_portfolio + deposit_base + npl_inventory). Page 91 mode banner added.
- **v7.11** ACL extended to customer_base + dormant_accounts. **5 of 6 stocks ACL-wired (~85%)**. capital_base intentionally remains engine-derived from CapitalAdequacyEngine (engine output is BETTER than ACL fallback for already-engine-computed stocks).

**Key insight:** The ACL pattern is the right boundary for stocks that exist in CBS tables (loans, deposits, customers, dormants, NPLs) but the wrong boundary for stocks that are computed (capital). Knowing when NOT to apply a pattern is as important as the pattern itself.

### Cards engine + L05 visibility (v7.12 → v7.13) — 2 batches

The platform's first "build engine + close loop + surface UI" sequence.

- **v7.12** Built `utils/cards.py` (new engine: usage_velocity + merchant_category_mix + geographic_pattern + card_usage_profile aggregator) + L05 CONSUMER `customer_segmentation.enrich_segment_with_card_usage()`. **L05 status flipped from DESIGNED_NOT_WIRED → WIRED**. **14 of 15 loops WIRED (93%).**
- **v7.13** Surfaced cards engine on page 34 Customer 360 Tab 5 with 5 illustrative scenarios — operators can pick a usage scenario, see the cards engine produce a PUBLISHED_LANGUAGE payload, watch the segmentation engine consume it.

**Key insight:** This is the canonical pattern for v8.x — build engine + wire loop + surface in one ~2-batch sequence. v8.x infrastructure batches can use this as the template when adding new engines (e.g. when L14 streaming closes).

### v8.x readiness infrastructure (v7.14) — 1 batch

The platform's CBS-synthetic tier became meaningful.

- **v7.14** `scripts/generate_cbs_aggregates.py` writer (~250 lines) produces 5 cbs_data/*_aggregate.json files. Running the script flips all 5 ACL-wired stocks from `data_source=demo_defaults` to `data_source=cbs_synthetic`. `mode=synthetic` is now a meaningful test environment.

**Key insight:** The 3-tier ACL fallback (live → CBS synthetic → demo defaults) only matters operationally when the synthetic tier has real files. v7.14 made it real.

### Audit hardening (v7.15) — 1 batch

The platform locked the v7.x pattern.

- **v7.15** G106 + G107 audit gates added. Discovered + fixed 2 latent registry corrections (L01 from_engine and L02 to_engine pointing to non-existent modules). **107 audit gates total.**

**Key insight:** Audit gates aren't bookkeeping — they're the platform's immune system. G106 + G107 immediately surfaced 2 issues that had been latent for batches; from v7.15 forward, this category of regression is permanently blocked.

## Cumulative invariants v7.x established

These patterns are now permanent — any future batch that violates them will fail audit.

1. **Stocks are explicitly tracked** (Charter §5). `system_stocks.SYSTEM_STOCKS` is the registry. Status enum: WIRED / NOT_WIRED. (G104 ratchet.)

2. **Feedback loops are explicitly designed** (Charter §6). `system_flows.FEEDBACK_LOOPS` is the registry. Status enum: WIRED / DESIGNED_NOT_WIRED / DEPRECATED. WIRED loops have importable from_engine + to_engine. (G106.)

3. **Regulated invariants live in a registry** (Charter §9). `system_invariants.SYSTEM_INVARIANTS` is the registry. 6 regulated engines (capital_adequacy, liquidity_risk, regulatory_reporting, stress_testing, treasury_intelligence, credit_risk_scoring) MUST import from registry, not hardcode thresholds. (G105 strict.)

4. **WIRED stocks declare their data_source provenance** (Rule 6 honesty discipline). Every snapshot stamps where values came from: `flexcube_aggregator: cbs_synthetic`, `flexcube_aggregator: demo_defaults`, `engine_derived`, etc. (G107.)

5. **ACL pattern for FLEXCUBE integration** (Charter §7). `flexcube_aggregator.py` is the seam. Mode-aware fallback. A2Z domain code never sees FLEXCUBE-specific field names.

6. **Composites are caller-driven and surfaced on per-domain pages** (Charter §13). `composite_scores.py` provides 4 composites. Each is surfaced on page 91 (systems view) + at least one per-domain page.

7. **Engine + loop + UI ship in 1-2 batches** (canonical pattern from v7.12/v7.13). Build engine → wire loop → surface UI. Future v8.x work follows this template.

## What v7.x didn't ship

Honest about scope boundaries:

1. **L14 (Channel reliability → Customer experience alerts)** — requires Kafka/CDC streaming infrastructure beyond v7.x scope. This is THE remaining unwired loop. Deferred to v8.x.

2. **Live FLEXCUBE handler implementations** — `_fetch_loan_portfolio_live()`, `_fetch_deposit_book_live()`, `_fetch_npl_live()`, `_fetch_customer_base_live()`, `_fetch_dormant_accounts_live()` are all stubs returning None. v8.x will wire them to flexcube_adapter calls or direct Apigee REST endpoints.

3. **`--from-cbs` flag in CBS writer** — v7.14 ships the writer with `--from-cbs` documented as v8.x stub. Actual aggregation from cbs_data/customers.json + accounts.json + transactions.json is v8.x work.

4. **Audit gates G108 + G109** — diminishing-returns hardening (payload field validation, charter cross-references) considered but not shipped. Available for future batches if regression patterns warrant.

5. **Engine-side observability** — every engine reads invariants via `get_threshold()` but there's no telemetry yet on how often each invariant is read. Could be future v8.x work to measure engine-registry coupling at runtime.

6. **Cross-aggregate LDR computation** — v7.10 deposit_base aggregator hardcodes `loan_book_basis_kes` for LDR computation; could be enhanced to compute from both loan + deposit aggregates.

## What worked particularly well

1. **Building the charter first (v7.0).** Every subsequent batch had a place to record decisions. The charter became the platform's spinal cord.

2. **The 1-batch-at-a-time discipline.** 24 consecutive clean-first-try runs is unusual; it came from each batch having one clear narrative ("close L04" or "wire customer_base ACL" or "surface IFRS 7") rather than bundled changes.

3. **Mid-batch self-correction (v7.15).** Adding G106 + G107 surfaced 2 latent registry inconsistencies. Fixing them in the same batch (rather than as a follow-up) preserved the 24-clean streak and proved the gates work.

4. **The "registry corrections" pattern.** 7 cumulative corrections to feedback loop registry entries (engine names that pointed to non-existent or renamed modules) — every one caught by either ACL wiring (v7.2-v7.6) or G106 (v7.15). The registry is now truth-aligned.

5. **The uniform expander pattern (v7.8).** One template applied 4 times for composite surfacing; reused once more in v7.13 for cards. Pattern reuse compounded the campaign's UI velocity.

6. **The 3-tier ACL fallback (live → CBS synthetic → demo defaults).** Designed in v7.10 for 3 stocks; extended in v7.11 to 5 stocks; made operational in v7.14 with the writer; locked by G107 in v7.15. Each step built on the previous without architectural rework.

7. **Charter §14 self-acknowledgement.** Every batch that touched the systems layer updated charter §14's "what's still open" section. By v7.15 this was down to 1 item (L14 streaming) — the campaign's exit criterion.

## What was tricky

1. **Knowing when NOT to apply a pattern.** v7.11 deliberately did NOT route capital_base through the ACL even though it had been wired through for 5 other stocks. Engine-derived is BETTER than ACL fallback for already-engine-computed stocks. Recognising this required pattern discipline, not pattern enthusiasm.

2. **G2 direct-I/O gate vs new foundational modules.** v7.10 added `flexcube_aggregator.py` which uses `read_text()` for CBS files. Initial audit ran 104/105 because the gate didn't know the new module is foundational. Fixed by adding it to FOUNDATIONAL list — same exemption used since v5.x for 16 other foundational I/O modules.

3. **Registry references vs reality.** 7 cumulative corrections in v7.x because the v7.0 registry was drafted from charter design notes; subsequent batches corrected as engines were actually wired. By v7.15 the corrections caught up; G106 now prevents new drift.

4. **The "100% stocks but only 85% ACL" frame.** Easy to over-claim "the systems layer is at 100%" when 100% of stocks are WIRED. Honest framing required tracking ACL-wiring separately from WIRING — the latter is structural, the former is operational.

---

## Lessons for v8.x

1. **The registry-first pattern works.** Future bounded contexts (e.g. streaming events for L14) should declare in the registry first, then wire incrementally. v7.0's charter took ~1 batch to write but saved 23 subsequent batches from architectural ambiguity.

2. **Ratcheting audit gates beat retrospective enforcement.** G104 + G105 + G106 + G107 all use the ratchet pattern (current state defines the floor; future batches can only improve). This converts each batch's progress into permanent floor without requiring retroactive cleanup.

3. **The "build engine + close loop + surface UI" 2-batch sequence is canonical.** v7.12/v7.13 demonstrated it for cards. v8.x can reuse this template for new engine domains.

4. **CBS-synthetic tier > demo defaults** as a primary path even when no live FLEXCUBE access is available. v7.14 proved that file-based synthetic data is enough to make `mode=synthetic` operationally meaningful.

5. **Mid-batch gate additions are productive.** v7.15 added 2 gates that immediately found 2 issues. The temptation is to add gates only when you "know" they'll pass; the better pattern is to add gates aggressively and fix what they catch in the same batch.
