### Dual-shape support

The baseline captures CBS state at two granularities:

**Always available (bank-level aggregates):**
- `deposits_aggregate` — total deposits, by stability tier, by product, by segment
- `loans_aggregate` — outstanding, by segment, by stage, PD, LGD
- `npl_aggregate` — Stage 3, NPL ratio, by aging
- `customer_aggregate` — counts by segment, tenure, channel, KYC risk
- `dormant_aggregate` — dormant accounts by tenure

**Conditionally available (when `accounts.csv` is present):**
- `per_rm` — every RM's portfolio: CASA, term deposits, retail/MSME/corporate loans, NPL, par, income, account counts
- `per_branch` — same metrics rolled up to branch

In Joshua's production environment, `accounts.csv` (or `cbs_accounts.csv`) is generated by `generate_cbs.py` and per-RM sections are fully populated. In the sandbox where only the bank aggregates exist, `per_rm` and `per_branch` are empty `{}` — the baseline is still structurally valid, just sparser.

### Two-file save pattern

`save_baseline()` writes to TWO paths atomically:

| Path | Purpose |
|---|---|
| `data/cbs_baseline_<YYYY>_<MMM>_<DD>.json` | Dated archive — IMMUTABLE after creation. Each snapshot date produces its own file. Historical record for multi-year YoY comparisons later. |
| `data/cbs_baseline.json` | Canonical current — overwritten on each save. Matches the schema filename so G230 can validate it. |

`load_baseline()` defaults to the most recent dated archive (typically the canonical current).

### Pattern Q — validate-before-save

`save_baseline()` calls `utils.schema_validator.validate_before_save("cbs_baseline.json", baseline)` before writing. If the baseline doesn't conform to `cbs_baseline.schema.json`, save raises `ValueError` instead of producing a malformed file. The schema is enforced at the producer, not just at consumer-read time.

### Schema `data/_schemas/cbs_baseline.schema.json`

Locks the baseline structure: `_doc`, `_schema_version`, `snapshot_date`, `snapshot_generated_at`, `source_cbs_files`, `bank_aggregates`, `per_rm`, `per_branch`, `summary`. Adds `cbs_baseline.json` to the G230 protected-files list automatically.

### CLI: `scripts/snapshot_cbs_baseline.py`

```bash
python scripts/snapshot_cbs_baseline.py 2025-12-31   # snapshot at year-end close
python scripts/snapshot_cbs_baseline.py              # snapshot at today's date
```

Idempotent for the same date — re-running overwrites the dated archive (which is fine if CBS state hasn't materially changed since). Different dates produce separate dated archives.

### Audit gate G240

Locks the baseline:
1. `data/cbs_baseline.json` exists (canonical current)
2. At least one dated snapshot exists (`data/cbs_baseline_*_*_*.json`)
3. The canonical file validates against the schema (delegates to G230)
4. `snapshot_date` is within sensible range (1990-01-01 to today+1y)
5. `_schema_version` is supported (currently `"1.0"`)
6. `summary.rm_count` and `summary.branch_count` are present

G240 runs in **0.0s** — just file existence + JSON parse + schema validation. Zero render cost.

## Comparison API for downstream batches

YoY growth math is exposed via `compare_*` helpers. Both return `(current_value, baseline_value, growth_pct)`. Growth is `None` when baseline is 0 (undefined, not infinity).

```python
from utils.cbs_baseline import load_baseline, compare_bank_aggregate
baseline = load_baseline()  # most recent
cur, base, growth = compare_bank_aggregate(
    current_total_deposits, baseline,
    "deposits_aggregate.total_deposits_kes",
)
# growth = 12.0 means 12% YoY growth
```

Items 3 (auto-refresh) and 4 (PBT from CBS) in subsequent batches will use these helpers extensively.
